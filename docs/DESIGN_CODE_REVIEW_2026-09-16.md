状態: レビューと修正計画のみ。アプリの実装・設定は変更していない。

## 結論

**基本設計は妥当であり、全面的な書き直しは不要。ただし、データ消失につながる
2件を優先して修正することを推奨する。**

3つの `WKWebView` と共有の永続 `WKWebsiteDataStore` は、独立した表示と
ログイン状態の共有という要件に合っている。AppKit の採用、WebKit 標準動作の
活用、最小限の Sandbox entitlement、外部アカウント不要のサンプルも維持してよい。
JavaScript の評価に失敗した場合に自動再読み込みを見送る方針も適切である。

主な弱点は、正常系ではなく、保存失敗・編集後のフォーカス移動・設定変更・
ポップアップ終了といった状態遷移にある。現状の自動再読み込みは DOM の一時的な
状態から安全性を推測しており、設計書の「下書きを失わない」という目標を満たさない。
ダウンロードにも、既存ファイルを保全してから確定する仕組みがない。

サンプルページ、インストールスクリプト、関連設計・配布文書を確認した。

- **実行確認**: 実装中のスクリプトを抽出し、非永続データストアの独立した

- **コード経路確認**: 条件分岐・コールバック・状態更新を追跡して確認できる問題。
- **API 契約確認**: インストール済み WebKit SDK のヘッダー、Apple の公式仕様、

### R1: ダウンロード上書き失敗で元のファイルを失う

保存パネルで既存のファイルを選択すると、`removeItem(at:)` でそのファイルを
削除してから WebKit に保存先を渡す。その後に通信切断・容量不足・アプリ終了等が
発生すると、元ファイルは戻らない。失敗コールバックはアラートを出すだけで、
復元処理も成功時の確定処理もない。

`WKDownloadDelegate` は、渡す保存先が未作成のファイルであることを要求する。
したがって、単に `removeItem` を削除するだけでは修正にならない。

**修正方針**: ダウンロード先をアプリが管理する一時ファイルにし、成功後だけ
ユーザー指定先へ安全に確定する。元ファイルは確定まで残す。失敗・キャンセル時は
そのダウンロード専用の一時ファイルだけを片付ける。Sandbox の許可範囲と
異なるボリュームへの保存を考慮し、確定処理の失敗でも元ファイルを消さない。

**受け入れ条件**: 上書き成功、通信断、確定失敗、保存パネルのキャンセルの各経路で
元ファイルの内容を確認する。失敗・キャンセルでは元ファイルが変化せず、
成功では完成した新ファイルだけが指定先に残る。

### R2: 下書き検出が X 固有の要素と textarea に偏っている

`hasDraft` は X 固有の `data-testid` と `textarea` だけを見る。
一般的な `contenteditable` や通常のテキスト入力は、フォーカスがある間だけ
`isEditing` で保護される。入力後にボタン等へフォーカスが移ると保護されない。
また、メイン文書だけの検査では iframe 内の編集中・メディア再生等を捕捉できず、
`[role="dialog"]` だけではネイティブの `<dialog>` を捕捉できない。

実装そのものの `reloadSafetyScript` に対して確認した代表例:

| ページ状態 | 必要な判定 | 現在の判定 |
|---|---|---|
| 読み取り専用の空ページ | 再読み込み可 | 可 |
| 文字入り `textarea` | 再読み込み不可 | 不可 |
| X の `tweetTextarea_0` に文字がある | 再読み込み不可 | 不可 |
| 文字入り `contenteditable` からボタンへフォーカスを移す | 再読み込み不可 | **可** |
| `input` を編集後、ボタンへフォーカスを移す | 再読み込み不可 | **可** |
| iframe 内の文字入り `textarea` にフォーカスがある | 再読み込み不可 | **可** |
| `dialog.showModal()` で開いたダイアログ | 再読み込み不可 | **可** |
| `role="dialog"` の表示要素 | 再読み込み不可 | 不可 |

この `false` 判定を受けた `autoReload()` は、読み込み中でなければページ全体を
再読み込みする。Web 側で永続化していない編集内容は失われる。

**修正方針**: 瞬間的なフォーカス判定だけでなく、入力・変更イベントに基づく
文書単位の編集状態を保持する。各フレームの状態、ネイティブのパネル表示中、
ネイティブ HTML ダイアログも考慮し、状態を確定できない場合は自動更新を見送る。
非同期評価にはナビゲーション世代を関連付け、古い文書の判定を新しい文書へ
適用しない。状態は文書の置換時にリセットする。

すべての Web アプリの「保存済み」を外部から完全には判定できないため、初期実装は
編集を検知した文書では自動再読み込みを止め、手動再読み込みを維持する保守的な
方針とする。クロスオリジン iframe や Shadow DOM の状態を捕捉できない場合の
扱いも明示し、「あらゆるサイトの下書きを保証する」とは説明しない。

**受け入れ条件**: 上表に加え、ファイル選択、再生中メディア、別オリジンの
iframe、WebKit / ネイティブのモーダル、評価中のページ遷移を対象とする。
編集後にフォーカスを外してタイマーの更新機会を迎えても、内容が維持されること。

### R3: 別カラムの設定変更で作業中のページまで破棄する

設定の保存コールバックは、保存前後の差分を取らず、3カラムすべてに
`loadConfiguredAddress` を呼ぶ。1カラムだけの URL 変更でも、他のカラムの
フォーム・スクロール位置・現在の遷移先が失われる。何も変更せず「保存」しても
同じ問題が起きる。自動再読み込みの安全判定はこの経路では使われない。

**修正方針**: 保存前後の設定値を比較し、変更したカラムだけを更新する。
変更対象に未保存の編集がある場合は、適用前に確認する。確認を取り消した場合は
設定の永続化も行わない。明示的な「設定済みページを開く」は、設定保存とは
別の全カラム移動操作として扱う。

**受け入れ条件**: 無変更の保存ではナビゲーションが0回。1カラム変更では対象だけが
移動し、他の2カラムの URL・下書き・スクロール位置を保つ。
サンプル表示中の設定保存についても、変更カラムだけに適用する方針で統一する。

### R4: HTTP 対応の表示と実際の通信ポリシーが不一致

設定画面とナビゲーションポリシーは `http` を許可し、エラーメッセージも
HTTP / HTTPS の両対応を案内する。一方、元の `Info.plist` にも生成済みアプリの
`Info.plist` にも ATS の例外はない。ATS の対象となる通常の平文 HTTP 接続は
拒否されるため、設定で受理されても表示できない URL が生じる。
ローカル通信などの例外まで「すべての HTTP が失敗する」という指摘ではない。
同じく ATS 例外を持たない独立したアプリバンドルの `WKWebView` で
`http://example.com/` を開き、`NSURLErrorDomain -1022` による拒否も確認した。

**修正方針**: 小型ブラウザとして現行の HTTP 対応仕様を維持するなら、
WebKit の Web コンテンツに限定した ATS 例外を検討する。
`NSAllowsArbitraryLoads` によるアプリ全体の無条件許可は行わない。
HTTPS を初期補完の既定とし、HTTP 表示時の識別と App Store 向けの例外理由を用意する。
HTTPS 専用へ仕様変更する場合は、設定・アドレス入力・文書・既存設定の扱いを
そろえる必要があり、単に現在の拒否動作を放置しない。

**受け入れ条件**: 配布形態のアプリで HTTP / HTTPS、HTTP から HTTPS への
リダイレクト、拒否される接続を確認し、仕様・表示・実動作が一致すること。

参考: [Apple: NSAllowsArbitraryLoadsInWebContent](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity/nsallowsarbitraryloadsinwebcontent)
は既定値 `NO`。`YES` の使用には App Store 審査で理由の説明が必要。

### R5: 空文字ホストを有効な設定とみなす

`URLComponents.host != nil` はホストが空文字でも成功する。
現在の Foundation では `http://`、`https://`、`https:///path` のすべてが
空文字のホストを返し、現在の検証を通過する。保存後の起動時にも使われるため、
一度の入力ミスが永続する。アドレス欄は別の正規化・検証を実装しており、
設定画面と同じポリシーを共有していない。

**修正方針**: URL の補完と検証を小さな共通型に集め、許可スキーム、
非空ホスト、実際に構築できる URL を確認する。設定値としての空欄は引き続き許可する。
保存用と一時的なアドレス入力の違いは入口で明示する。

**受け入れ条件**: 上記3例は保存不可。空欄と正常な HTTP / HTTPS は仕様どおり処理し、
URL の日本語・ポート・IPv6・パス・クエリを誤って拒否しない。

### R6: JavaScript で閉じたポップアップが残る

`createWebViewWith` で生成した `WKWebView` はネイティブウィンドウに入れて
保持されるが、`webViewDidClose(_:)` が実装されていない。
SDK の契約では DOM の `window.close()` 成功後、アプリ側がビューを取り除き、
対応するウィンドウ等を閉じる必要がある。現状は手動で閉じる経路しかない。

**修正方針**: ポップアップの WebView と controller を対応付け、
`webViewDidClose` で該当するポップアップだけを閉じる。手動終了とスクリプト終了で
同じ後片付けを行い、メインカラムは閉じない。

**受け入れ条件**: 開いた子ウィンドウからの `window.close()` で、そのウィンドウと
保持参照が解放される。複数のポップアップ、手動終了、親ウィンドウ終了も確認する。
特定の認証サービスが必ず失敗するという指摘ではなく、終了操作の欠落の指摘である。

### R7: 読み込み失敗が無表示で終わる

`didFail` と `didFailProvisionalNavigation` はボタン状態を更新するだけで、
渡されたエラーを使用しない。DNS エラー、通信断、TLS / ATS 拒否等が起きても、
失敗した URL と原因をアプリ側から確認できない。以前のページが残る場合には、
入力した URL と実際の表示内容も混同しやすい。

**修正方針**: 失敗したナビゲーションを識別して、対象カラムまたはポップアップに
再試行可能な失敗表示を出す。通常の遷移キャンセルやダウンロードへの移行は
失敗通知の対象から除外し、過去のリクエストの失敗で新しいページを上書きしない。
TLS 検証を無効化して解決しない。

**受け入れ条件**: 到達不能なホスト、通信断、証明書エラーで原因と対象を識別できる。
直後に別 URL を開いた場合や、正常なダウンロードでは不要なエラー表示を出さない。

### R8: ダウンロードの発生元ウィンドウが失われる

メインカラムとそのポップアップは同じ `BrowserColumnView` を delegate として使う。
`didBecome download` の時点では発生元 `webView` が分かるが、保存処理へ引き継がない。
保存パネルとダウンロードエラー表示は常に `self.webView`、つまりメインカラム側へ
提示される。そのため、ポップアップで開始した操作への応答が別ウィンドウに出る。

**修正方針**: ダウンロード単位に発生元、指定保存先、一時保存先を管理する。
保存・エラー表示は発生元へ出す。発生元が閉じた場合の通知先・キャンセル方針も
明示し、終了済みのビューを不必要に保持しない。R1 の作業状態管理と一緒に直す。

**受け入れ条件**: メインカラムと複数ポップアップから同時にダウンロードを開始し、
各パネル・失敗表示・保存結果が別の操作へ混ざらない。

## 設計面の改善方針

`main.swift` が991行であること自体を不具合とは判断しない。ただし
`BrowserColumnView` は描画・URL 解釈・ナビゲーション・自動更新・ダウンロード・
ポップアップ・各種パネルを兼務しており、R8 のような所有者の混同が起きている。

責務の分離は、今回修正する境界に絞る。

| 境界 | 担当するもの | 維持するもの |
|---|---|---|
| URL 入力処理 | 正規化、検証、エラーの分類 | 設定の保存キーと既定値 |
| 再読み込みポリシー | 編集状態、フレーム状態、世代、ネイティブ操作中の抑制 | 長い更新間隔、手動更新、評価失敗時の抑制 |
| ダウンロード管理 | 発生元、ファイル保全、成功時の確定、終了処理 | OS 標準の保存パネル |
| カラム表示 | ツールバー、WebView、状態表示 | 3カラム固定、共有データストア |

全面的な MVVM 化、SwiftUI 化、DI フレームワーク導入、汎用ブラウザ基盤の新設は不要。
純粋な判定をテスト可能にし、WebKit / AppKit delegate は薄く保つ程度でよい。

また、自動更新と `XPullToRefresh.js` は編集・モーダル・メディアの判定を
別々に実装している。後者の可視性判定は新着ボタンを画面上端で探す用途と
ダイアログの検出で共用されているため、同じ意味の「安全」を共有できていない。
共通の安全状態と、各機能固有の発火条件を分ける。X のボタンを押す動作と
ページ全体の再読み込みは別操作なので、単純に処理全体を共通化しない。

テストターゲットは Swift Package / Xcode とも存在しない。
修正時には関係する回帰確認を同じ変更に含め、テスト基盤のためだけの大規模な
事前リファクタリングは避ける。Xcode 構成は `project.yml` を正として生成する。

## 修正プラン

各段階は別の変更としてレビューできる単位とし、回帰確認を後回しにしない。

| 順序 | 対象 | 変更内容 | 完了条件 |
|---|---|---|---|
| 1 | R1・R8 | ダウンロード単位の状態管理を導入し、一時保存から成功時の確定へ変更。発生元へ UI を提示 | 失敗時の元ファイル保全、成功時の置換、複数発生元の独立性 |
| 2 | R2・R3 | 保守的な編集状態追跡、更新抑制、文書世代の管理、設定の差分適用 | 編集・iframe・モーダル時に自動更新しない。無変更の保存で移動しない |
| 3 | R4・R5・R7 | 共通 URL 入力処理、HTTP 方針と ATS の整合、対象別の失敗表示 | 無効入力を保存しない。受理した通信方式が仕様どおり動作し、失敗を識別できる |
| 4 | R6 | ポップアップの WebView / controller 対応付けと終了処理 | スクリプトと手動の双方で正しい子ウィンドウだけを解放 |

段階1と2を最優先とする。段階3の HTTP ポリシーは、配布仕様と審査説明を含めて
確定させてから実装する。各段階で関係する README、設計書、日英表示を更新する。

| 分類 | 維持・確認する内容 |
